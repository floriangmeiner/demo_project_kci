# Build System

How the STM32F746G-DISCO firmware is built and flashed, how our makefiles work
with the one CubeMX generates, and which tools are used.

Last checked on Nov 27, 2026. The build gives no warnings, and its flash image
is byte-for-byte identical to the one CubeMX's own Makefile produces. Flashing
works on the board.

## Quick commands

Run these from the repo root.

| Task | Command |
| ---- | ------- |
| Build | `make` |
| Build and flash | `make flash` |
| Show section sizes | `make size` |
| Delete the build output | `make clean` |
| Debug | Open `tools/debug/kepler_demo_ozone_setup.jdebug` in Ozone |
| Check the tools | `tools/embedded_dev_tooling/toolchain.sh verify stm32` |

`make` builds in parallel on all CPU cores unless you pass your own `-j`.
Every build prints the RAM and flash use at the end.

Flashing and debugging are explained in
[tools/debug/README.md](../tools/debug/README.md).

## Layout

```text
Makefile                    what you run: make, make flash, make size, ...
mk/
  cube.mk                   reads CubeMX's Makefile for its files and flags
  common.mk                 toolchain, flags and build rules
app/
  Makefile                  the application: CubeMX code plus our code
  src/, inc/                our code (planned, starting with RTT logging)
kepler_demo_stm32f746g-disco/
  Makefile                  generated by CubeMX: read, never run by us
  Core/, Drivers/, ...      generated code: HAL, FreeRTOS, lwIP, startup
vendors/segger/rtt/         third-party source we build (planned)
tools/debug/                flash script and Ozone project
build/app/                  output, ignored by git
```

## How it works with CubeMX's Makefile

**CubeMX's Makefile is a list we read, not a build we run.** CubeMX decides
*what* its code is: which files, include folders and chip flags. Our makefiles
decide *how* to build it, *what else* to add, and *where* the output goes.

```text
CubeMX writes ──> kepler_demo_stm32f746g-disco/Makefile
                    C_SOURCES, ASM_SOURCES, C_INCLUDES,
                    C_DEFS, MCU, LDSCRIPT, LIBS
                          │
                          │  include: read its variables only
                          v
mk/cube.mk       adds the folder prefix to every path,
                 and stops the build if a file is missing
                          │
                          v
app/Makefile     CubeMX lists + app/src/*.c
                          │  flags and rules from mk/common.mk
                          v
build/app/       kepler_demo_app.elf, .hex, .bin, .map
```

### Reading the variables

GNU Make's `include` reads another makefile as if its text were pasted in, so
all its variables become available. Its paths are relative to the CubeMX
folder, so [`mk/cube.mk`](../mk/cube.mk) puts that folder in front of each one
and copies the result into `CUBE_*` variables:

| Generated variable | Copied to | Holds |
| ------------------ | --------- | ----- |
| `C_SOURCES` | `CUBE_C` | The 125 C files: HAL, FreeRTOS, lwIP and `Core/Src` |
| `ASM_SOURCES`, `ASMM_SOURCES` | `CUBE_ASM` | `startup_stm32f746xx.s` |
| `C_INCLUDES` | `CUBE_INC` | 25 include folders |
| `C_DEFS` | `CUBE_DEFS` | `-DUSE_HAL_DRIVER -DSTM32F746xx` |
| `MCU` | `CUBE_MCU` | CPU and FPU flags |
| `LDSCRIPT` | `CUBE_LDSCRIPT` | `STM32F746xx_FLASH.ld` |
| `LIBS` | `CUBE_LIBS` | `-lc -lm -lnosys` |

Everything else in the generated Makefile is ignored: its rules, `CFLAGS`,
`LDFLAGS`, `BUILD_DIR`, `TARGET`, `OPT` and `DEBUG`.
[`mk/common.mk`](../mk/common.mk) sets our own.

### Keeping its rules out of the way

Including a makefile brings its rules along, not just its variables:

| Brought in | Why it doesn't interfere |
| ---------- | ------------------------ |
| `all`, its first target, would become the default | `mk/cube.mk` clears `.DEFAULT_GOAL`, and `app/Makefile` sets it to `firmware` |
| Rules for `build/%.o`, `.elf`, `.hex` and `.bin`, and `clean` | They refer to a `build/` folder inside `app/`, so they never match our output in `build/app/` at the repo root. Our `clean` is in the top-level `Makefile` |
| `-include build/*.d` | Finds nothing from `app/`, so it does nothing |
| Variables such as `TARGET`, `CC` and `BUILD_DIR` | Anything with the same name set *before* the include is overwritten. So `app/Makefile` includes `mk/cube.mk` first and sets its own values after it |

That last row isn't theoretical: the first version of `app/Makefile` set
`TARGET` above the include, and the output came out named after the CubeMX
project.

### Failing loudly

`mk/cube.mk` stops the build with an error if:
- the generated Makefile has no `C_SOURCES` or `MCU`, for example because a
  CubeMX version renamed them;
- a file it lists doesn't exist.

Without this, a renamed variable would give an empty file list and a confusing
link error, or a build missing half the HAL.

### When you use CubeMX

| You do | What changes in our build |
| ------ | ------------------------- |
| Change settings and click Generate Code | Nothing to do. The next `make` reads the new lists, and rebuilds everything because a makefile changed |
| Turn on a peripheral, such as I2C3 in Slice 8 | CubeMX adds the HAL file to its list, and our build picks it up |
| Add a `.c` file to `app/src/` | Picked up automatically: `app/Makefile` builds every `.c` file there |
| Edit the generated Makefile | Don't. CubeMX overwrites it |

The generated Makefile still works on its own (`make` inside the CubeMX
folder), with its output in `kepler_demo_stm32f746g-disco/build/`. That's
useful for the check below.

## Checking our build matches CubeMX's

While `app/src/` is empty, our build compiles exactly the code CubeMX's
Makefile does, with the same flags, so the two images should be identical:

```bash
make
make -C kepler_demo_stm32f746g-disco -j$(nproc)
cmp build/app/kepler_demo_app.bin kepler_demo_stm32f746g-disco/build/kepler_demo_stm32f746g-disco.bin
```

`cmp` printing nothing means they're byte-for-byte the same. That was the case
on Nov 27. Once our own code is added, compare `.text` sizes with `make size`
instead.

The images only matched after adding `-fmacro-prefix-map`. Before that, our
build's lwIP assert messages, which contain the source file's path from
`__FILE__`, started with `../kepler_demo_stm32f746g-disco/`. That added 512
bytes of read-only data, though the code itself was already identical.

## Compiler and linker settings

Set in [`mk/common.mk`](../mk/common.mk). They match the generated Makefile's,
with three additions.

| Setting | Value | Notes |
| ------- | ----- | ----- |
| CPU and FPU | `-mcpu=cortex-m7 -mthumb -mfpu=fpv5-sp-d16 -mfloat-abi=hard` | From CubeMX. The FPU is single precision only, so `double` maths runs in software |
| Defines | `USE_HAL_DRIVER`, `STM32F746xx` | From CubeMX |
| Optimization | `-Og` | `FW_OPT`; same as CubeMX's default |
| Debug info | `-g -gdwarf-2` | When `FW_DEBUG=1`, the default |
| Warnings | `-Wall` everywhere; also `-Wextra` for `app/` | **Added.** The HAL and lwIP give many `-Wextra` warnings, which would hide ours |
| C standard | `-std=gnu17` | **Added.** It's GCC 13's default, so nothing changes; it just stays fixed |
| `__FILE__` paths | `-fmacro-prefix-map` | **Added.** CubeMX files show as `LWIP/Target/...`, ours as `app/src/...` |
| Dead code removal | `-fdata-sections -ffunction-sections`, `--gc-sections` | Unused functions and data are dropped at link time |
| C library | newlib-nano (`-specs=nano.specs`), `-lc -lm -lnosys` | From CubeMX |
| Linker script | `kepler_demo_stm32f746g-disco/STM32F746xx_FLASH.ld` | From CubeMX |
| Memory report | `-Wl,--print-memory-usage` | Printed on every link |
| Compiler path | `arm-none-eabi-gcc` from `PATH`, or `make GCC_PATH=...` | As in the generated Makefile |

**Object files mirror the source tree** under `build/app/obj/`, and keep the
source extension: `Core/Src/main.c` becomes `.../Core/Src/main.c.o`. The
generated Makefile puts every object in one folder, so two files with the same
name would collide. None do today, but our code and the vendored code make it
more likely.

**Dependencies:** `-MMD -MP` writes a `.d` file next to each object, so a
changed header rebuilds the files that include it. A changed makefile,
including the generated one, rebuilds everything.

The linker script gives the firmware two regions:

| Region | Start | Size | Holds |
| ------ | ----- | ---- | ----- |
| `FLASH` | `0x08000000` | 1 MB | Code and constants |
| `RAM` | `0x20000000` | 320 KB | Data, the FreeRTOS heap and the main stack |

### Build outputs

In `build/app/`, which `.gitignore` excludes:

| File | What it is | Used by |
| ---- | ---------- | ------- |
| `kepler_demo_app.elf` | Program with debug symbols | Ozone, `make size`, GDB |
| `kepler_demo_app.hex` | Intel HEX image, with addresses | `tools/debug/flash_app.jlink` |
| `kepler_demo_app.bin` | Raw image, no addresses | Later: signing and TFTP updates |
| `kepler_demo_app.map` | Linker map: where every symbol went | Checking memory placement |
| `obj/` | Objects and dependency files | `make` itself |

### Memory use

Printed at the end of every build. On Nov 27:

| Region | Used | Size | Used |
| ------ | ---- | ---- | ---- |
| RAM | 72,872 B | 320 KB | 22% |
| FLASH | 75,124 B | 1 MB | 7% |

lwIP's heap isn't counted in RAM. `LWIP_RAM_HEAP_POINTER` fixes it at
`0x20048000` instead of letting the linker place it. See [Memory
placement](peripheral_ETH.md#memory-placement).

## CubeMX regeneration

Generate Code in CubeMX rewrites the `Makefile` and every generated source file.

- **The generated `Makefile` has no `USER CODE` blocks,** so any edit to it is
  lost. Our makefiles are where build changes go.
- **Source files keep their `USER CODE` blocks,** because the `.ioc` has
  `ProjectManager.KeepUserCode=true`. Code outside the blocks is overwritten.
- **`ProjectManager.DeletePrevious=true`** deletes generated files that CubeMX
  no longer generates, for example if a middleware is turned off. It doesn't
  touch our folders.

## Tools

| Tool | Version | From | Used for |
| ---- | ------- | ---- | -------- |
| `arm-none-eabi-gcc` | 13.2.1 | Ubuntu apt, `gcc-arm-none-eabi` | Compiling and linking |
| GNU Make | 4.3 | Ubuntu apt | Running the makefiles |
| STM32CubeMX | 6.18.1 | ST | Generating the HAL code and the Makefile we read |
| J-Link software | V978 | SEGGER | Flashing (`JLinkExe`), RTT viewer, GDB server |
| Ozone | V350a | SEGGER | Debugging |
| SystemView | V410b | SEGGER | Thread tracing, not set up yet |
| SEGGER RTT source | V8.58 | SEGGER on GitHub | Logging, copied into `vendors/segger/rtt/`, not built yet |

`tools/embedded_dev_tooling/toolchain.sh` installs and checks these versions,
and `configs/stm32.conf` lists them. See its
[README](../tools/embedded_dev_tooling/README.md). The SEGGER tools and CubeMX
are linked into `~/.embedded-tools/bin`, which `~/.bashrc` adds to `PATH`.

The board's on-board ST-LINK has been reflashed with J-Link firmware, so use
the SEGGER tools, not ST's.
